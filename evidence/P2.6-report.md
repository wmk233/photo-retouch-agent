## 一、用户 8 个必答问题

### 1. 重复 Vision 计费是否已修复？— **是**

根因：点击「AI 设计三套造型」时前端串行发起

1. `POST /api/photos/analyze`（付费 Vision #1）
2. `POST /api/styling/proposals`（`styling_planner` 内再走一次付费 Vision #2）

而 UI 只提示「1 次模型调用」，实际计费 2 次且无缓存。

已修复：

- 新增按「图像内容 SHA256 + domain + provider/模型/密钥指纹」为键的分析缓存
  （`backend/app/infrastructure/analysis_cache.py`，LRU + TTL，可用
  `PHOTO_AGENT_ANALYSIS_CACHE_TTL` / `PHOTO_AGENT_ANALYSIS_CACHE_MAX` 关闭）。
- `AnalyzePhoto`（`backend/app/application/use_cases.py`）命中缓存时直接返回
  既有分析，只改 `image_id` 并置 `analysis_reused=True`，**不重复调用 Vision**。
  复用的是 provider 自己的原话，人物事实未被编造或跳过分析。
- 计费如实上报：`/styling/providers` 现在返回
  `stylingAiAnalysisRequests=1`、`stylingAiDesignRequests=1`、
  `stylingAiFlowRequests=2`，AI 模式带 `analysisRequests/designRequests/
  paidRequests=2/reusedAnalysisRequests`；`costNote`/`billingNote` 明确写清
  「1 次分析 + 1 次设计 = 2 次；命中缓存时只计 1 次」。
- 前端 `estimateStylingCost(..., { analysisReused })` 与 `app.js` 的进度/成功/
  费用文案均按「2 次」或「复用后 1 次」分别提示；按钮文案与初始 costNote 同步更新。
- 测试：`backend/tests/test_analysis_cache.py`（13 项）覆盖内容指纹命中/失配、
  provider 指纹隔离、TTL/LRU/`clear`、禁用开关、复用语义与 `analysisReused` 透传；
  前端 `frontend/tests/styling-workflow.test.mjs` 断言复用透传与
  `paidDesignRequests==1`。

**边界（如实说明）**：只消除可省的那一次分析调用。第二次 `styling/proposals`
必须真实调用视觉模型来「设计三套造型」，本轮**不合并两个 planner**（越界、风险高），
因此首次点击仍是 2 次付费调用，第二次起为 1 次。

### 2. SiliconFlow 是否真正提供可用的原生 Mask API？— **UNSUPPORTED（否）**

- 官方图片端点仅 `POST /images/generations` 一个（OpenAPI 3.0.0，license MIT）。
- 请求体 `oneOf` 全枚举 10 个 schema：`FLUX.2-pro`、`FLUX.2-flex`、
  `Qwen-Image`、`Z-Image`、`FLUX.1-Kontext`、`FLUX.1-Kontext-dev`、
  `FLUX-1.1-pro`、`FLUX-1.1-pro-Ultra`、`FLUX.1-schnell`、`FLUX.1-dev`。
- **全部字段中不存在 `mask`**；只有 `image` / `input_image` / `image_prompt`
  （image2 / image-prompt，语义是参考图/强度，**不是 mask**）。
- 文档全文 grep `mask` / `inpaint` / `img2img` / `图生图` / `局部` → **0 命中**。

结论：SiliconFlow 目前**没有**原生局部重绘（mask inpainting）接口。
**严禁把 `image2`/`image_prompt` 当作 mask 使用**。

### 3. 哪个现成 GitHub Inpainting 方案最适合直接使用？

| 方案 | 许可证 | image+mask+prompt | 权重获取 | 适配结论 |
|---|---|---|---|---|
| `huggingface/diffusers` `AutoPipelineForInpainting` | Apache-2.0 | 是（`mask_image`，白=重绘/黑=保留） | HF 官方（SD1.5-inpainting 15.2GB；SDXL-inpainting 20.8GB） | **首选**：标准 mask 语义、SD/SDXL/SD3 通吃、文档与社区最好 |
| `TencentARC/BrushNet` | Apache-2.0（含第三方声明） | 是（自带插件 + base 模型） | Google Drive（非 HF 一键），需自备 SD1.5/SDXL | 次选：质量潜力高，但权重分发不便、作者称工业级需自训 |

**最适合直接使用：`AutoPipelineForInpainting` + SDXL inpainting 权重**，
因为它的 mask 语义与本地 `edit_mask.py` 完全一致（白=重绘），且许可证宽松。

### 5. 预计需要什么硬件或云端费用？

- 本地 SDXL inpainting：全量权重 20.82 GB，**fp16 推理约需 ≥ 8–12 GB 显存**；
  SD1.5-inpainting 全量 15.23 GB，约 4–6 GB 显存可跑。本机无独立推理条件。
- BrushNet：需 PyTorch 1.12.1 + CUDA 11.6 环境 + 额外 ckpt + base 模型。
- fal.ai：图像 inpainting 走 A100/H100；`flux-*-fill` 按**百万像素四舍五入**计费，
  `fal-ai/inpaint` 走 GPU-A100。**具体单价未在公开 list 接口暴露，必须在 fal 控制台核对**（本轮未取到，不臆测）。

- **缺口如实上报**（写入 `gaps`）：`hair_band_is_geometric`、`clothing_band_is_geometric`

  **不是分割结果**，边界是启发式；矩形同时覆盖了颈、臂、背景等同带像素。

### 7. 能否保持未编辑五官不变？— **能（几何层面），视觉验收 `VISUAL_ACCEPTANCE_PENDING`**

- 五官/眉毛/鼻子/外唇来自真实 MediaPipe 面网格（`fill_feature_guard`）；
- **牙齿与笑容**由内唇凸包一并保护（张嘴微笑时牙齿在同一凸包内）；
- 面部皮肤用「被试者本人肤色」的自适应判定保护，避免把额头碎发当成皮肤冻结；
- `protected = max(features, face_skin)`，`editable` 由 `protected` 相减而来 →
  **五官像素与 editable 交集恒为 0**（`identityCoversEditable=True` 可断言）；
- `preserve = bitwise_not(editable)` 保证「未选中区域 = 原图」。
